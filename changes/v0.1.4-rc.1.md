# v0.1.4-rc.1 (2026-09-08)

**Pre-release (pre-release channel)**: candidate for the `0.1.4` stable release, published ahead of it for verification. Content matches `changes/v0.1.4.md` (the upstream-parity v0.85.0+ main line + M5 closeout) plus the RC update channel introduced in this file; at stable-release time this file's entries fold into `v0.1.4.md`. Install: existing rpi users run `rpi update --rc` (or `rpi update --all --rc` to also update the four lockstep extensions to `0.1.4-rc.1`); install.sh does not serve RCs (`releases/latest` stays stable).

## New in this RC (not part of the upstream-parity main line; first appears with rc.1)

- **RC update channel** (V14-19, an rpi-native requirement): `rpi update --rc` updates the binary to the latest RC, `rpi update --extensions --rc` updates extensions to the latest RC versions; without `--rc` the channel is always stable; the channel is a one-shot command flag, never persisted; pre-release builds automatically probe the RC endpoint for the startup version check (banner marked pre-release, pointing to `rpi update --rc`); an rc build switches back to stable by running plain `rpi update` (no flag). Release process and version-number rules (`<stable>-rc.<N>`) live in the `RELEASING.md` RC section.

## Verification requests (the point of the RC)

- Self-update path on all six targets (`rpi update --rc` download + sha256 verification + atomic replacement; Windows gets manual-replacement instructions)
- `rpi update --extensions --rc`: the four lockstep extensions (subagents / mcp-adapter / smart-fetch / statusline) going 0.1.3 → 0.1.4-rc.1; without `--rc` they stay at 0.1.3 (the stable channel filters prereleases)
- The upstream-parity v0.85.0+ behavioral surface (the 18-task list is in `changes/v0.1.4.md`)

Known boundary: the RC endpoint (`https://revpi.dev/api/latest-rc-version.json`) goes live once the Release assets are in place; self-hosted mirrors must provide the file in the same directory.
