# v0.1.5-rc.6 (2026-09-29)

**Pre-release (pre-release channel)**: candidate for the `0.1.5` stable release. Content = `v0.1.5-rc.5` plus the batch below; at stable-release time this file's entries fold into `v0.1.5.md`. Upgrade: `rpi update --rc` (or `rpi update --all --rc` to also move the six lockstep extensions to `0.1.5-rc.6`).

One real-use fix, reported against rc.5 as issue #55: a subagent's `contact_supervisor({reason: "need_decision"})` ask never reached the parent session — the reviewer card sat on `⎿ contact_supervisor reason=need_decision` until the child's 10-minute reply timeout burned out, and the parent (idle after an async launch, or blocked inside a foreground dispatch) never saw the question at all.

## Fixed in this RC

- **Supervisor asks wake the parent again (issue #55)** — the pi-subagents port had dropped upstream's entire parent-side delivery face (`native-supervisor-channel.ts` `poll()`, L706-757: the channel poller that turns a new reply-expecting request into a `sendMessage` with `triggerTurn: true`). The child side and the `subagent_supervisor` reply tool were ported; the wake in between was not — the only ask discovery paths left were the in-wait attention checks, which require the parent to already be blocking inside `bg_wait`. Both faces are restored: (1) **async runs** — the fleet refresh loop (already ticking every 500 ms while runs are alive) now scans the supervisor-channel root each tick and sends exactly one `subagent_supervisor_request` message with `triggerTurn: true` per new session-owned blocking ask, deduped across ticks, retried on a host error (the request file stays; `subagent_supervisor({action:"pending"})` still lists it); the message content is upstream's `requestVisibleText` shape — the child-formatted title/run/agent/child context, the question body, and a `Reply with: subagent_supervisor({ action: "reply", replyTo: "<id>", ... })` hint naming the request id. (2) **foreground (blocking) single runs** — the wait loop polls the child's channel on the existing cadence (500 ms non-streaming, the 1 s activity tick streaming); on a blocking ask it fires the same triggerTurn message, then **detaches** the dispatch (upstream `INTERCOM_DETACH_REQUEST_EVENT` → `detachForeground("intercom coordination")`, gated on the intercom bridge being active — the `allowIntercomDetach` equivalent): the tool call returns a `Detached for intercom coordination` receipt pointing at the ask, the still-running child registers in the async registry (`status` / `wait` / the fleet strip / `stop` all see it, `run.detached` event, best-effort `maxActiveAsyncRunsPerSession` slot), and a background continuation drives the run tail to completion — pipes drained, result synthesized and persisted, and the completion session message arrives exactly like an async run's, with `record_step_result` + the shared `finish` path writing the terminal state. The queued ask message triggers the parent's next turn as soon as the detached receipt returns, so the decision lands inside the child's reply window instead of after its timeout. Also corrected: the `p1/supervisor.rs` comment that had scoped the missing watcher's impact to `progress_update` ("identical net semantics") — `need_decision`/`interview_request` delivery depends on the same face. Known limits, deliberate for this RC: composite sync paths (`tasks`/`steps` without `async`) still do not detach (the observed blocking face is the single delegation; composites dispatch async by construction in practice), and steering a detached run is not wired — `stop` works through the registered handle. Pinned by three new tests: the session-ask projection + visible-text/reply-hint shape, the fleet delivery send-once/dedupe/triggerTurn contract, and an e2e detach scenario (fixed-child slow mode with a watcher thread dropping a `need_decision` request into the live channel) asserting the receipt returns before the child finishes, the triggerTurn ask message carries the reply hint, and the completion notify lands from the continuation.

## Verification requests

- **Foreground ask (the reported scenario)**: run a reviewer-style delegation that hits a decision and calls `contact_supervisor` with `need_decision` — the tool call should return a `Detached for intercom coordination` receipt within ~1 s of the ask (not after a 10-minute stall), a "Subagent needs a decision" session message should arrive carrying the question and the `Reply with:` hint, `subagent({action:"status"})` should list the run as running, and after `subagent_supervisor({action:"reply", replyTo:"<id>", message:"..."})` the child should resume and its completion should arrive as a session message.
- **Async ask**: repeat with `async: true` and yield the turn — the same ask message should wake the idle parent within ~1 s, without any `bg_wait` in flight.
- **Regression sweep**: ordinary foreground/async delegations without asks behave exactly as before (no extra messages, no detach path taken).
