# v0.1.9-rc.4 (2026-11-28)

**Pre-release (pre-release channel)**: the fourth candidate for the `0.1.9` stable release, adding the Windows startup self-update (ADR-0050). The rc.1 feature set (upstream parity to Pi v1.5.2, the streaming-performance and Linux-memory main line, the statusline `estimate` calculation mode, the provider/MCP/coding-agent increments and the `rpi-subagents` / `rpi-smart-fetch` rebase), the rc.2 fix and the rc.3 fix are unchanged — see `changes/v0.1.9-rc.1.md`, `changes/v0.1.9-rc.2.md`, `changes/v0.1.9-rc.3.md` and `changes/v0.1.9.md`; at stable-release time this file's entries fold into `changes/v0.1.9.md`. Install: existing rpi users run `rpi update --rc` (or `rpi update --all --rc` to also move the seven lockstep extensions to `0.1.9-rc.4`); install.sh does not serve RCs (`releases/latest` stays stable at `0.1.8`). This RC does not change any registry, schema, model-catalog or version endpoint beyond the RC endpoint and the profile index of this RC (ADR-0042: assets before endpoints).

## New in this RC

- **Windows: `rpi update` takes effect at the next start instead of stopping at manual steps** (`rpi`, ADR-0050). A running program cannot be replaced on Windows, so until now `rpi update --self` printed instructions and exited 1. It now downloads and verifies the release into `.update\staging\` next to `rpi.exe`, writes `pending.json` and prints `Downloaded rpi <version>. It takes effect the next time rpi starts.` (exit 0); with `--all` the extensions of the same batch are staged with it. The next start — before argument dispatch and before any extension loads — takes an OS-level exclusive lock, re-verifies every staged file (sha256, and that the installation was not changed by a re-run of the installer in between), and swaps the extensions, their pointers, the executable (two back-to-back renames: the running image is parked as `rpi.exe.old-<version>`) and the install manifest in one journaled transaction whose undo data is persisted before the first change. The old process then starts the new `rpi.exe` with the original command line and waits for it, so the shell prompt (cmd, PowerShell, Windows Terminal, VS Code) returns only when rpi exits, the exit code passes through and Ctrl+C reaches the new instance only; the new instance sits in a kill-on-close job, so closing the terminal ends it too. `rpi update` on top of an update that already waits for its first start prints `rpi <version> is already downloaded and waits for its first start to be confirmed` and exits 0.
- **First-start confirmation and automatic rollback** (`rpi`): the new version confirms itself at known-good points (`--help`, `--version`, an argument error, a one-shot command that exits 0, the TUI main loop, the `rpc` and `json` modes). If it terminates before that — a crash, a kill — the previous executable, extension pointers and install manifest are restored, the failed version is written to the block list and rpi says `The update to rpi <new> failed and was rolled back to rpi <old>`; `rpi update --self --force` stages that version again. Every event goes to `%LOCALAPPDATA%\rpi\logs\update.log` (rotated at 1 MiB).
- **Extensions install as versioned directories on Windows** (`rpi`, `install.ps1`): `rpi install`, `rpi update --extensions` and the installer place a package under `<extensions>\<name>\<version>\` and flip an atomically written `current.json` pointer instead of replacing files a running instance may have loaded. Layouts written by earlier versions keep loading (`rpi list`, `rpi update --extensions` and the loader resolve both), `/reload` stays on the generation the instance started with, `rpi remove` retires the whole container, and each running rpi process registers a pin so a generation in use is never deleted. The installer only writes the new layout for versions that read it (`0.1.9-rc.4` and later) and repairs a missing `rpi.exe` before installing when a parked `rpi.exe.old-*` exists.
- **Startup cleanup and notices** (`rpi`): every start removes old-version files that no running instance uses any more and, in the interactive startup notice, says `Updated rpi <old> → <new>` once (and whether the previous version was already removed or other running instances still use it), or warns while old files are still in use or could not be deleted; non-interactive runs write those warnings to stderr only. `rpi update --cleanup` retries the cleanup (exit 0 when nothing remains, 1 otherwise); `rpi self-uninstall` refuses while other rpi instances use the installation and lists the update leftovers.
- Nothing changes on Linux and macOS: the startup path, the in-place self-update, the in-place extension replacement and `install.sh` are byte-for-byte the rc.3 behavior.

## Breaking changes in this RC

None for Linux/macOS. On Windows the on-disk layout gains `.update\` state files, `rpi.exe.old-<version>` / `rpi.exe.bad-<version>` images, versioned extension directories with `current.json` pointers, `.pins\` registrations and `%LOCALAPPDATA%\rpi\logs\update.log`; the pre-`0.1.9-rc.4` flat extension layout stays readable. A `rpi` older than `0.1.9-rc.4` does not read the generational layout: after updating extensions on Windows, keep running `0.1.9-rc.4` or later (downgrading the host below it needs `rpi update --self --version <old>`, whose extensions then have to be reinstalled flat by that older version's installer).

## Verification requests (the point of this RC)

This RC's Windows runtime behavior was developed without a Windows machine: the state machine, journal, rollback, pins, cleanup and pointer logic are unit-tested on Linux with per-step fault injection, both PowerShell installer suites run on Linux pwsh 7 and the `#[cfg(windows)]` code is cross-compiled and linted for `x86_64-pc-windows-gnu` (plus a small in-tree ZIP reader checked byte-for-byte against the published rc.3 Windows asset). None of the following has been executed on Windows yet — every item is a request:

- **Getting to rc.4**: an installed `0.1.9-rc.3` or older has no staging code, so its `rpi update --self` still prints the manual instructions — install `0.1.9-rc.4` with `install.ps1` (rpi closed) and check `%USERPROFILE%\.rpi\agent\extensions\<name>\current.json` names `0.1.9-rc.4` and that the plugins load.
- **Update and switch-over** (needs a release newer than the installed one: the stable `0.1.9` once published, or a later RC): run `rpi update --self --rc` (expect the `Downloaded rpi <version>. It takes effect the next time rpi starts.` line and exit 0, `rpi.exe` unchanged, `.update\pending.json` present), then start rpi from cmd, from PowerShell, from Windows Terminal and from the VS Code terminal: the new version must come up, `rpi --version` must print the new version afterwards, the prompt must return only when rpi exits, and the exit code must pass through (`rpi --version; echo %ERRORLEVEL%`). Ctrl+C must reach the new instance only. Then `rpi update --all --rc` for the extensions: after the next start, `%USERPROFILE%\.rpi\agent\extensions\<name>\current.json` must name the new version and the plugins must load. `rpi update --all` while rpi is already current applies the extension updates right away.
- **Two instances**: with one rpi (`0.1.9-rc.4` or later) still open in another window, run `rpi update --all --rc` and start a second rpi: the second runs the new version with the new extension generation, the first keeps running undisturbed and switches over after it restarts; while it is open, the second instance's startup shows `1 other running rpi instance is still on rpi <old>` on the first-start notice and then the in-use warning on later starts, and `rpi.exe.old-<old>` disappears at the first start after the old instance has exited. Instances older than `0.1.9-rc.4` write no pins: close them before updating extensions.
- **Rollback**: after staging an update (from the newer installed version to a yet newer one, or with `rpi update --self --version <installed> --force` to re-stage the current version), start rpi and end the *new* process (Task Manager → end the newest `rpi.exe`, the child — not the trampoline) before the TUI is up: rpi must report `The update to rpi <new> failed and was rolled back to rpi <old>`, restart on the old version, `rpi --version` must print it, and a plain `rpi update --self` must refuse with the block-list message until `--force` is added. Counter-cases that must not roll back: `rpi --version` / `rpi --help` / a mistyped command as the first start, a one-shot command that fails, Ctrl+C during the first start, `rpi --resume` with the picker cancelled.
- **Cleanup**: `rpi update --cleanup` exits 0 with `Nothing left to clean up` on a settled installation and 1 while an old instance keeps files in use; `rpi self-uninstall` refuses while another rpi is open.
- **Installer**: `install.ps1` on a machine with `0.1.9-rc.3` installed (rpi closed) upgrades to rc.4 with the generational plugin layout (`extensions\rpi-todo\0.1.9-rc.4\` and `current.json`); re-running it with `rpi.exe` renamed away but a `rpi.exe.old-*` present prints `restored the parked executable ...` and installs.
- The earlier verification requests remain open: from rc.3, `edit` on CJK text in fullscreen and regular mode; from rc.2, fullscreen mode over a restored session; from rc.1, the BREAKING surfaces on real providers, the performance main line on real hardware and the plugin line.
- `scripts\windows-update-verify.ps1` (`-List` prints this matrix with its phases) drives the automatable steps and asserts the on-disk state of each phase.

Known limits (design §11.7): shutting Windows down before the new version confirmed its first start counts as that crash (rollback, block list); a crash after the confirmation is not rolled back — the previous image stays as `rpi.exe.old-<version>` until the next normal exit, and `install.ps1` or a manual rename restores it; targets older than `0.1.9-rc.4` switch without the first-start check; subagent children spawned by an instance that predates the update run the new version; if rpi dies exactly between its two renames, `rpi.exe` is missing until `install.ps1` or a manual rename restores it.

Known boundary: the RC endpoint (`https://revpi.dev/api/latest-rc-version.json`) and the `0.1.9-rc.4` profile index go live only after the Release assets are in place; the stable endpoint (`latest-version`), the schema/model-catalog files and the extension registry entries for stable stay at their current values. The rc.4 source — after the first independent review and its remediation — passed the local Linux gates before tagging — `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo check --workspace --all-targets --locked` on the stable toolchain (rustc 1.98.1) and on 1.95.0, `cargo test --workspace` (253 result lines, 9601 passed, 0 failed, 9 ignored), the `install.sh` suite (275 checks) and the PowerShell installer suites on Linux pwsh 7 (253 and 69 checks) — and its `#[cfg(windows)]` code cross-compiles and lints cleanly for `x86_64-pc-windows-gnu` (rpi and every workspace crate except `rpi-ext-smart-fetch`, whose BoringSSL build does not cross-compile, and `rpi-durable`, which does not compile on Windows at all); the new manually dispatched `windows-tests` workflow (format, clippy, check, the update tests, the Windows-only probes and both PowerShell installer suites under PowerShell 7 and Windows PowerShell 5.1) has not been run on a Windows runner yet, and neither has the Windows matrix above.
