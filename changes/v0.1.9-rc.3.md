# v0.1.9-rc.3 (2026-11-27)

**Pre-release (pre-release channel)**: the third candidate for the `0.1.9` stable release, carrying the fix for the `edit` tool panic that a long fullscreen session ran into (`tokio-rt-worker`: `byte index N is not a char boundary`). The rc.1 feature set (upstream parity to Pi v1.5.2, the streaming-performance and Linux-memory main line, the statusline `estimate` calculation mode, the provider/MCP/coding-agent increments and the `rpi-subagents` / `rpi-smart-fetch` rebase) and the rc.2 fix are unchanged — see `changes/v0.1.9-rc.1.md`, `changes/v0.1.9-rc.2.md` and `changes/v0.1.9.md`; at stable-release time this file's entries fold into `changes/v0.1.9.md`. Install: existing rpi users run `rpi update --rc` (or `rpi update --all --rc` to also move the seven lockstep extensions to `0.1.9-rc.3`); install.sh does not serve RCs (`releases/latest` stays stable at `0.1.8`). This RC does not change any registry, schema, model-catalog or version endpoint beyond the RC endpoint and the profile index of this RC (ADR-0042: assets before endpoints).

## Fixed in this RC

- **The `edit` tool no longer panics with `byte index N is not a char boundary` on files with multi-byte text around the edited block** (`rpi`): the windowed diff the tool returns in `details.diff` / `details.patch` located the window of each replacement with `str` slices at `match_index - 1` (`line_start_before`) and at `match_end - 1` (the end of the last touched line), and the 32-line margin walk sliced at `start - 2`, the last byte of the character before the line feed. Each of those indices lies inside a multi-byte character as soon as the old text starts or ends right next to one (an ideographic full stop, a full-width comma or parenthesis, a CJK word, an emoji) or as soon as one of the lines in front of the window ends with one, so on CJK text every edit panicked unless both edges of the old text touched ASCII and so did all of the up to 32 lines in front of it — on the tokio worker thread (`edit_diff.rs:1226`, the byte index landing inside U+3002), before the write: the edit was not applied and the panic text was printed while the fullscreen UI was running, and a long session meets its first such edit sooner or later. The three line lookups (`line_start_before`, the window-end search, `count_line_feeds`) now run on bytes — `\n` is ASCII and never part of a multi-byte sequence, so the result is the same and no longer depends on a char boundary. The whole-file oracle added with the fix (a randomised differential test of the windowed diff against a diff of the complete file: 1–4-byte characters, up to 5 edits per file, merged and separate windows, files with and without a trailing newline) also caught two display defects of the same windowing: the ` ...` fold marker inside a window was laid out with the window's — narrower — line-number width instead of the file's, and the collapse of the two markers between neighbouring windows compared the raw line, so a file of 100+ lines with edits near its top printed the marker twice. Regression tests: the `edit_diff_window_*` cases in `crates/rpi/tests/edit_diff.rs` and `test_edit_multibyte_neighbours_mid_file` in `crates/rpi/tests/edit.rs` (all panic at the reported sites with the fix reverted); the oracle runs 600 seeds in the suite (asserting that at least half of them reach the comparison) and passed 100,000-seed and 20,000-seed soaks, the latter with up to 400 lines and 12 edits per file.

## Verification requests (the point of this RC)

- `edit` on CJK text, in fullscreen and in regular mode: an edit whose old text starts or ends right next to a multi-byte character (after an ideographic full stop, a CJK word, an emoji), or that has a line ending in such a character among the 32 lines in front of it, must apply and return its diff — no `tokio-rt-worker` panic `byte index N is not a char boundary; it is inside …`. On rc.1 and rc.2 nearly every edit in a Chinese file failed this way, so a few ordinary edits in such a file are enough. In the returned diff, the ` ...` fold markers should match a whole-file diff's: aligned with the file's line-number width, and a single marker between two edits that are far apart.
- The earlier verification requests remain open: from rc.2, fullscreen mode (alt-screen) over a restored session — switch themes from `/theme` (and once with the auto theme setting), run `/clear`, navigate with `/tree` and let an auto-compaction finish while frames render — must keep rendering (no `rpi-tui-driver` panic `index out of bounds`); from rc.1, the Windows settings/auth/keybindings lock fix on a real Windows machine, the BREAKING surfaces on real providers, the performance main line on real hardware and the plugin line.

Known boundary: the RC endpoint (`https://revpi.dev/api/latest-rc-version.json`) and the `0.1.9-rc.3` profile index go live only after the Release assets are in place; the stable endpoint (`latest-version`), the schema/model-catalog files and the extension registry entries for stable stay at their current values.
