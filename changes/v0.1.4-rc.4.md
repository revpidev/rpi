# v0.1.4-rc.4 (2026-09-08)

**Pre-release (pre-release channel)**: round four of the `0.1.4` stable candidates, fixing two hot-switch/fullscreen interaction defects found during rc.3 verification (independently confirmed twice: PTY end-to-end reproduction + unit-test-level conclusions). The baseline content matches `changes/v0.1.4.md`; at stable-release time each rc file's entries fold into `v0.1.4.md`. Install/upgrade: existing rpi users run `rpi update --rc` (or `rpi update --all --rc` to sync extensions to `0.1.4-rc.4`); force-install via the official script with `RPI_GITHUB_API_URL=https://api.github.com/repos/revpidev/rpi/releases/tags/v0.1.4-rc.4`.

## Fixes relative to rc.3 (found in rc.3 verification)

- **Live refresh freezing after hot-switching the display mode — "one keystroke, one frame"** (confirmed by PTY end-to-end reproduction): after switching TUI mode in `/settings` (either direction), all event-driven re-rendering stopped working — streaming replies, the working indicator, and the status bar no longer reached the screen, and only keystrokes forced a frame (the input-dispatch path's immediate rendering), presenting as "input frozen". Root cause: the `RenderHandle` returned by `TuiHandle::render_handle` froze the **creating renderer's** scheduler into a `Weak` — after `switch_tui_mode` swapped in a new renderer and the old one was dropped, `upgrade()` failed → every event-driven `request_render` (agent message updates / subscription callbacks / spinner timer / footer) silently no-oped, and the new renderer's `next_deadline` stayed `None` so the driver thread never refreshed proactively. Fix: aligned with upstream's `createInteractiveTuiReference` Proxy semantics (tui-renderer.ts:66-96) — the `render_handle` closure now resolves the current renderer through a slot inside TuiHandle **at call time** and marks its scheduler; the `Weak` no-life-extension contract is preserved (a handle outliving the TUI still safely no-ops). Interactive mode captures this handle once at init and distributes it to all holders (the editor's autocomplete debounce thread, spinner, footer, subscription callbacks) — a single-point fix covers everything. Regressions: `render_handle_reaches_the_renderer_swapped_in_later` (rpi-tui, both-direction swaps + driver deadline assertions, red with the fix reverted) and `switch_tui_mode_render_requests_reach_swapped_renderer` (rpi, event path); PTY end-to-end: a real `/settings` hot-switch → streaming replies reach the screen continuously without keystrokes, verified both directions (reproducing "reply missing until a keystroke" before the fix).
- **Keyboard input dying after clicking the editor/selector area in fullscreen** (a companion suspicion from the investigation, settled at unit-test level): in fullscreen, a left click (press+release synthesized as click) on any row of the docked editor area moved keyboard focus to the editor container's **wrapper layer** — `Container::handle_input` is a no-op, so all subsequent keys were swallowed (transcript-area clicks were unaffected). Root cause: upstream's `Container.prototype.handleMouse` (tui.ts:355-358) forwards via `dispatchMouseEvent(child)` and leaves `focusTarget` to the **child component** (a plain Container has no `handleInput` and doesn't take over), while the ported `Container::handle_mouse` returned only the bare result, so the outermost dispatcher pinned focus to the container entry; `SharedEntry` exists precisely to preserve the child's shared identity (the focus target). Fix: `SharedEntry::handle_mouse` now resolves via `dispatch_mouse_event(self.0)` (`Forwarded` passthrough, same shape as mouse-region.ts:26) — the gesture target and focus target return to the inner shared component, and the keyboard keeps working after clicking the editor/selector. Regression: `fullscreen_left_click_across_dock_keeps_editor_focus_and_input` (rpi, a 4-column × full-row click matrix over the dock area of a 24-row terminal + per-cell keypress assertions; rows 20-24 went red across all columns before the fix); PTY end-to-end: fullscreen start → transcript/editor-row/per-row clicks → input probes all echo back.
